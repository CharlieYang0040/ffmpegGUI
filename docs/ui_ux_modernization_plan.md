# ffmpegGUI UI/UX 현대화 개발 계획

최초 작성일: 2026-07-30

> 완료 상태: 이 계획의 작업 흐름, 상태 모델, 프리셋, 사전 검사와 비모달
> 진행 UI는 2.0에 반영됐다. 후속 기준은
> [development_plan.md](development_plan.md)를 따른다.

## 1. 제품이 필요한 이유

ffmpegGUI의 핵심 가치는 FFmpeg 명령을 숨기는 데 그치지 않는다. 영상, 가변
프레임 영상, 이미지 시퀀스, 애니메이션 WebP를 한 작업 목록에서 확인하고,
프레임 단위로 필요한 구간만 정한 뒤 CPU 또는 NVENC 프리셋으로 안전하게
변환하는 것이 이 앱의 이유다.

사용자가 가장 자주 수행하는 작업은 다음 네 가지다.

1. 여러 소스를 원하는 순서로 추가한다.
2. 미리보기와 타임라인에서 사용할 구간을 확인한다.
3. 결과 용도에 맞는 프리셋과 저장 위치를 정한다.
4. 실행 전 문제를 확인하고 인코딩한다.

새 UI는 이 순서를 그대로 보여주고, FFmpeg 경로·업데이트·OTIO·디버그 같은
낮은 빈도의 기능은 기본 작업에서 분리한다.

## 2. 현재 UI의 핵심 문제

### 정보 구조

- 세 개 패널에 기능이 나뉘어 있지만 작업 순서와 시각적 우선순위가 없다.
- `Job Inspector`, `Preflight`, `Tools / Advanced`처럼 한글·영문 용어가
  섞여 있고 기능의 의미를 처음 봐서는 알기 어렵다.
- 출력 경로와 FFmpeg 실행 파일 경로가 같은 수준으로 노출된다.
- 파일 정렬·이동용 버튼 일곱 개가 항상 보이며 소스 목록보다 눈에 띈다.
- 프리셋, FPS, 해상도, 개별 트림, 전체 트림의 적용 범위가 구분되지 않는다.
- 하단 진행 영역이 작업하지 않을 때도 큰 공간을 계속 차지한다.

### 상호작용

- 사용자가 무엇을 먼저 해야 하는지 빈 화면에서 안내하지 않는다.
- 자동 출력 경로·자동 파일명·폴더명 기준이 작은 체크박스로 나열되어
  상호 관계와 최종 결과 경로를 예측하기 어렵다.
- 실행 가능 여부는 표시되지만 문제를 해결할 다음 행동으로 연결되지 않는다.
- 프리셋 이름만으로 CPU/GPU, 속도, 품질, 결과 형식을 비교하기 어렵다.
- 자주 쓰는 “추가, 구간 설정, 용도 선택, 실행”과 유지보수 도구가 섞여 있다.
- 이모지 문자는 운영체제 글꼴에 따라 모양과 정렬이 달라 일관성이 떨어진다.

### 시각 체계와 접근성

- 거의 모든 배경과 테두리의 명도 차이가 작아 영역 구분이 약하다.
- 기본 글자, 보조 설명, 경고, 주요 행동의 크기와 굵기 체계가 부족하다.
- 버튼 상태가 색상에 과도하게 의존하고 키보드 포커스 표시가 약하다.
- 고정 너비와 촘촘한 버튼 배치가 Windows 배율 125~200%에서 불리하다.

## 3. UX 원칙

1. **작업 순서를 화면 순서로 표현한다.** 소스 → 구간 → 결과 → 실행 순서를
   거슬러 찾지 않게 한다.
2. **자주 쓰는 것은 한 번에, 드물게 쓰는 것은 필요할 때만 보인다.**
3. **설정보다 결과를 먼저 보여준다.** 코덱 옵션보다 예상 파일 형식, 해상도,
   FPS, 저장 위치를 먼저 표시한다.
4. **자동 설정은 예측 가능해야 한다.** 최종 출력 경로를 실행 전에 항상
   한 줄로 보여준다.
5. **오류는 해결 행동을 포함한다.** “NVENC 불가”에서 끝내지 않고 CPU
   프리셋 전환 또는 설정 열기를 제공한다.
6. **전문 기능은 제거하지 않고 격리한다.** OTIO와 세부 FFmpeg 옵션은
   고급 작업 공간에서 유지한다.
7. **UI 상태의 단일 원천을 만든다.** 위젯 값을 서로 복사하는 방식 대신
   현재 작업 모델을 화면이 구독하도록 점진적으로 전환한다.

## 4. 목표 사용자 흐름

### 빠른 변환

앱 실행 → 파일 끌어놓기 → 용도 프리셋 선택 → 저장 위치 확인 → 변환 시작

### 프레임 단위 구간 편집

파일 선택 → 미리보기/타임라인에서 시작·끝 지정 → 목록에서 구간 요약 확인
→ 다음 파일 선택 → 변환 시작

### 간단한 컷 편집

소스 선택 → 재생 헤드를 자를 위치로 이동 → `분할` → 필요 없는 클립 삭제
또는 각 클립의 양끝을 드래그 → 클립 순서 정리 → 하나의 결과로 변환

### 이미지 시퀀스

대표 프레임 또는 패턴 추가 → 감지된 프레임 범위 확인 → FPS 선택 또는 기본값
확인 → 미리보기 → 변환

### 문제 해결

실행 전 검사 카드 확인 → 해당 문제의 바로가기 선택 → 수정된 최종 결과 요약
확인 → 변환

## 5. 새 정보 구조

### 상단 앱 바

- 앱 이름과 현재 작업명
- `새 작업`, `설정`, `도움말`
- FFmpeg 준비 상태와 GPU 사용 가능 상태를 작은 상태 표시로 제공
- 업데이트, FFmpeg 경로, 디버그 모드는 `설정`으로 이동

### 왼쪽: 소스

- 큰 드롭 영역과 `파일/시퀀스 추가` 기본 버튼
- 목록 각 행에 썸네일, 파일명, 형식, 해상도/FPS, 구간, 경고 표시
- 행 안의 드래그 핸들로 순서 변경
- 선택 항목의 `삭제`만 기본 노출
- 정렬, 역순, 전체 삭제, 실행 취소는 `⋯` 메뉴와 단축키로 이동
- 빈 상태에는 지원 형식과 첫 행동을 설명

### 가운데: 미리보기와 구간

- 미리보기를 가장 큰 영역으로 유지
- 재생 제어와 속도를 한 줄로 단순화
- 타임라인 아래에 `시작`, `끝`, `선택 길이`를 함께 표시
- 개별 구간과 전체 추가 트림을 명확히 구분
- 손상 프레임이나 재생 오류는 미리보기 안에서 복구 행동과 함께 표시

### 오른쪽: 결과

- 최상단에 용도 중심 프리셋 카드:
  `빠른 검토`, `고품질 보관`, `GPU 빠른 변환`, `WebM`, `직접 설정`
- 선택한 프리셋의 결과 형식·코덱·예상 해상도·FPS를 요약
- 저장 위치와 최종 파일명 미리보기
- 실행 전 검사는 정상일 때 한 줄, 문제가 있을 때만 펼쳐진 카드로 표시
- 하단에 화면에서 가장 명확한 단일 기본 행동 `변환 시작`
- FPS·해상도·세부 코덱은 `세부 설정`을 열 때만 표시

### 하단 작업 서랍

- 대기 중에는 접힌 한 줄 상태 표시
- 실행 중 자동으로 펼쳐 진행률, 현재 파일, 남은 작업, 취소를 표시
- 상세 로그는 `로그 보기`에서만 노출
- 완료 시 `결과 폴더 열기`, `결과를 목록에 추가`, `다시 실행` 제공

### 별도 고급 작업 공간

- OTIO 가져오기/내보내기
- 직접 FFmpeg 옵션
- 버전 번호 올림/내림 규칙
- 진단 로그와 환경 정보

이 기능은 기본 화면의 `고급 도구`에서 열며 초보 사용자의 기본 경로를
방해하지 않는다.

## 7. 컴포넌트와 상태 구조

현재 `FFmpegGui`에 생성·상태·동기화 책임이 집중되어 있으므로 화면만 한 번에
교체하면 회귀 위험이 크다. 다음 경계를 먼저 만든다.

- `WorkspaceState`: 편집 클립 목록, 선택 클립, 출력 설정
- `SourcePanel`: 파일 추가·순서·선택과 항목 요약
- `PreviewPanel`: 재생과 현재 선택 항목의 구간 편집
- `OutputPanel`: 프리셋, 경로, 결과 요약, 실행 전 검사
- `JobDrawer`: 진행·취소·완료 행동
- `SettingsDialog`: FFmpeg, 업데이트, 테마, 진단
- `AdvancedToolsDialog`: OTIO와 직접 옵션
- `ThemeTokens`: 색상, 간격, 글자, 모서리, 상태 색상의 단일 정의

기존 코어 처리 결과는 유지하되 `EncodingJob`은 호환 어댑터를 거쳐 새 클립
계약으로 점진 이행한다. 새 UI와 백엔드를 동시에 교체하지 않고 각 단계에서
기존 작업과 동일한 결과를 확인한다.

## 8. 컷 편집 모델과 프론트엔드-백엔드 연결

### 현재 구조가 복잡한 이유

현재 하나의 구간이 다음 형태로 반복 표현된다.

- 목록 행의 `시작/끝` 1-based 프레임
- 타임라인의 `in_point/out_point`
- `encoding_job_adapter`가 만드는 앞/뒤 제거량
- `FrameTrim(head_frames, tail_frames)`
- 선택적으로 다시 더해지는 전역 앞/뒤 트림
- 이전 호출 경로를 위한 문자열·실수·초 단위 추정 변환

선택된 항목은 타임라인 값을 사용하고 나머지는 목록 위젯 값을 사용하는
예외도 있다. 따라서 화면 상태와 실제 인코딩 값이 달라질 가능성이 있고,
메타데이터가 늦게 도착할 때 값을 서로 되돌려 쓰는 방어 코드가 필요해졌다.

### 새 단일 구간 계약

내부에서는 앞/뒤에서 몇 프레임을 버릴지 저장하지 않는다. 각 클립이 사용할
원본 구간만 저장한다.

```python
@dataclass(frozen=True)
class ClipRange:
    source_in: int       # 0-based, 포함
    source_out: int      # 0-based, 미포함

@dataclass(frozen=True)
class EditClip:
    clip_id: str
    source_path: str
    source_range: ClipRange
    source_frame_count: int
    source_fps: float | None
```

`source_out`을 미포함으로 두면 선택 길이는 항상
`source_out - source_in`이며 빈 구간과 경계 검사가 단순해진다. UI만 사람에게
익숙한 1-based 포함 범위로 표시한다. 예를 들어 화면의 `16–90`은 내부에서
`[15, 90)`이고 정확히 75프레임이다.

원칙:

- `WorkspaceState`의 클립 구간이 유일한 편집 상태다.
- 목록과 타임라인은 같은 상태를 표시하고 명령을 보낼 뿐 서로 값을 복사하지
  않는다.
- 백엔드도 가능한 한 `ClipRange`를 그대로 받는다.
- `FrameTrim`은 기존 처리기 호환 경계에서만 일시적으로 계산하고 최종적으로
  제거한다.
- 초 단위인지 프레임 단위인지 값의 크기로 추측하는 로직은 제거한다.
- 기본 화면의 전역 트림은 제거한다. 여러 클립을 한꺼번에 조정하는 기능이
  필요하면 “선택한 클립에 동일한 구간 조정”이라는 명시적 일괄 명령으로
  제공하고 실행 즉시 각 `ClipRange`에 반영한다.

### 간단한 컷 편집의 범위

첫 버전은 전문 NLE가 아니라 단일 트랙 컷 편집으로 제한한다.

- 클립 양끝 조절
- 현재 위치를 시작/끝으로 지정 (`I`, `O`)
- 재생 헤드에서 클립 분할
- 클립 삭제, 복제, 순서 변경
- 같은 원본에서 여러 구간 사용
- 여러 클립을 목록 순서대로 하나의 결과로 연결
- 모든 구간 초기화

첫 버전에서 제외:

- 겹치는 비디오/오디오 트랙
- 트랜지션, 효과, 자막, 키프레임
- 원본 오디오와 영상의 독립 편집
- 리플·롤·슬립 같은 전문 편집 도구

### 프론트엔드 데이터 흐름

```text
사용자 조작
  → EditCommand(SetRange / SplitClip / DeleteClip / ReorderClip)
  → WorkspaceState.edit_sequence
  → SourcePanel + PreviewPanel + OutputSummary 동시 갱신
  → BuildEncodingJob
  → EncodingJob.clips
  → Preflight
  → FFmpeg 실행 계획
```

구체적인 동작:

1. 소스를 추가하면 전체 범위의 `EditClip` 하나를 만든다.
2. 타임라인 핸들, 숫자 입력, `I/O` 단축키는 모두 `SetRange` 명령을 보낸다.
3. `분할`은 현재 클립 `[in, out)`을 `[in, playhead)`와
   `[playhead, out)` 두 클립으로 원자적으로 교체한다.
4. 실행 취소는 위젯 값을 복원하지 않고 이전 `edit_sequence` 상태를 복원한다.
5. 메타데이터 도착 전에는 구간을 `pending`으로 두고, 프레임 수가 확인되면
   한 번만 유효 범위로 정규화한다.
6. 현재 선택 여부와 관계없이 모든 클립은 동일한 상태에서 작업으로 변환된다.

### 백엔드 연결

새 `EncodingJob`은 미디어 파일과 앞/뒤 제거량 목록 대신 순서가 있는
`EditClip` 목록을 받는다. 실행 계획 작성기가 미디어 종류별로 명시적인
프레임 범위를 변환한다.

- 영상: `select=between(n,start,end)`에서 `end=source_out-1`
- 이미지 시퀀스: 시작 번호와 프레임 개수를 `ClipRange`에서 계산
- WebP: 추출된 프레임 목록에 동일한 반개방 범위 적용
- 오디오: 영상 프레임 범위를 소스 FPS 기준 시간 범위로 변환
- 병합: 각 클립 결과를 `edit_sequence` 순서대로 연결

기존 `BatchProcessor`의 문자열/실수 보정, 전역 트림 덧셈, `trim_values`
덮어쓰기는 호환 어댑터 뒤로 격리한 후 제거한다. 미디어 처리기는 이미
검증된 FFmpeg 필터를 유지하되 입력 계약만 명확한 범위 객체로 바꾼다.

### 컷 편집 오류와 사전 검사

- `source_in < source_out <= source_frame_count`를 작업 생성 전에 검사
- 1프레임 미만 클립, 메타데이터 미확정 클립, 사라진 원본은 실행 차단
- 서로 다른 해상도·FPS·오디오 구성은 결과 프리셋 기준으로 정규화한다고 표시
- VFR은 UI 프레임 번호와 실제 타임스탬프 대응을 실행 계획에 명시
- 분할과 삭제 후 빈 작업이 되면 실행 버튼을 비활성화하고 이유 표시

### 이행 전략

1. `ClipRange`, `EditClip`, `EditSequence`와 경계 검사를 코어 모델에 추가한다.
2. 기존 `FrameTrim` 작업과 완전히 같은 FFmpeg 범위를 만드는 호환 어댑터를
   추가하고 계약 테스트를 작성한다.
3. `WorkspaceState`가 새 클립 모델을 소유하도록 하고 기존 목록/타임라인을
   읽기 전용 뷰로 연결한다.
4. 양끝 조절과 `I/O`부터 새 명령으로 전환한다.
5. 분할·삭제·복제·재정렬 명령을 추가한다.
6. `EncodingJob`과 사전 검사, 처리기를 `EditClip` 입력으로 전환한다.
7. 전역 트림과 위젯 간 동기화 코드, 레거시 초/프레임 추정 코드를 제거한다.

완료 조건:

- 화면의 한 클립당 편집 상태는 `ClipRange` 하나뿐임
- 목록, 타임라인, 결과 요약, 실제 인코딩 프레임 수가 같은 범위를 사용
- 선택 항목과 비선택 항목이 동일한 경로로 작업에 수집됨
- 분할 후 두 클립의 길이 합이 분할 전 길이와 정확히 같음
- 삭제·복제·재정렬·실행 취소 후 구간과 순서가 보존됨
- 영상, VFR, PNG 시퀀스, WebP에서 첫/마지막 프레임 경계 테스트 통과
- 레거시 `global_trim`, `trim_values`, 값 유형 추정 경로가 제거됨

## 10. 구현 우선순위와 범위 제한

첫 번째 출시 단위는 Phase 0~4다. 여기까지가 실제 사용성 개선이며, 단순
테마 변경만 먼저 출시하지 않는다. Phase 5~6은 핵심 흐름이 안정된 뒤
완료한다.

이번 현대화에서 하지 않는 것:

- 코어 인코딩 엔진 전면 재작성
- C++ 이식
- 다중 트랙 영상 편집기나 효과 편집기 추가
- 웹 기술로 UI 프레임워크 교체
- 성능 측정만을 위한 별도 장기 단계

검증은 각 Phase의 기능 완료 확인에 필요한 만큼만 수행하며, 개발을 멈추고
측정 기준만 확장하지 않는다.

## 11. 전체 인수 기준

- 처음 사용하는 사람이 별도 설명 없이 파일 추가부터 변환 시작까지 도달
- 자주 쓰는 기본 흐름에서 고급 옵션이나 FFmpeg 경로를 볼 필요가 없음
- 현재 지원하는 MP4, VFR, PNG 시퀀스, WebP, CPU, NVENC 기능을 모두 유지
- 클립 순서, 각 `ClipRange`, FPS, 출력 형식이 화면과 실제 결과에서 일치
- 분할·삭제·복제·재정렬만으로 단일 트랙 컷 편집을 완료할 수 있음
- 1280×720 및 Windows 100~200% 배율에서 핵심 컨트롤이 잘리지 않음
- 키보드 포커스와 오류 설명이 명확하고 색상만으로 상태를 전달하지 않음
- 취소 후 잔류 프로세스나 불완전 출력이 없고 즉시 재실행 가능
- 기존 자동 테스트와 실제 미디어 회귀가 모두 통과

## 12. 바로 시작할 개발 묶음

1. `ClipRange`, `EditClip`, `EditSequence`와 기존 `FrameTrim` 호환
   어댑터를 만든다.
2. `WorkspaceState`가 새 클립 목록을 소유하도록 연결한다.
3. 디자인 토큰과 공통 `Card`, `SectionHeader`, `StatusBadge`,
   `PrimaryButton` 스타일을 만든다.
4. 새 앱 바와 3열 골격을 기존 컴포넌트 위에 먼저 적용한다.
5. 소스 패널을 새 클립 행 컴포넌트로 교체한다.
6. 타임라인의 구간 변경과 분할을 새 명령 모델로 연결한다.
7. 결과 패널과 실행 전 검사 행동을 교체한다.

각 묶음은 실제로 동작하는 화면 단위로 끝내며, 전체 목업을 만든 뒤 한꺼번에
연결하는 방식은 사용하지 않는다.
